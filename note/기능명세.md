# RunPassport 백엔드 기능명세

> 이 문서는 `note/기능명세참고.md`(제품/기획 방향)와 이 저장소 (`runpassport-api`)에서 실제로
> 진행된 개발 내용 (코드, 마이그레이션, `develop-ticket.md`/`current-ticket.md`/`ai/code-review/*`
> 이력)을 근거로 작성함. **"기획됨"과 "실제 구현됨"을 구분해서 표기** — 기획 문서만 보고 이미 되는
> 것처럼 착각하지 않도록 하는 게 이 문서의 목적.
>
> 범위: 이 레포는 **백엔드 (Supabase Postgres + Spring Boot API)** 만 다룸. Android 앱, 웹 대시보드는
> 별도 레포/작업이라 여기서는 "이 백엔드가 뭘 준비해줘야 하는지" 관점에서만 언급.

---

## 0. 제품 개요 (기획 근거: `기능명세참고.md`)

GPS 인증 러닝 코스 스탬프 투어 + 지역 리워드 연계 앱. 핵심 후크: "오늘 서울은 65점인데 강릉 해안은 92점 — 주말에 뛰러 가실래요?" — 러닝지수로 지역을 추천하고, 실제 방문 (완주)하면 그
**지역**에 스탬프가 쌓이고, 스탬프로 그 지역 제휴매장 쿠폰을 받는 구조. "특정 지자체에 리워드가 귀속된다"는 점이 지자체 예산 명분과 직결되는 이 서비스의 핵심 설계 원칙.

원칙 (기획 확정, 재검토 불필요):

- 공공 API (두루누비/TourAPI/기상청/에어코리아)는 **런타임에 직접 호출 금지** — 배치로 사전 수집 후 자체 DB만 조회 (속도, API 쿼터 보호, 데모 안정성)
- 스탬프는 **단일 통화**(마일리지와 이중으로 안 만듦), 지자체 (지역) 단위로 귀속
- 완주 판정은 체크인이 아니라 **GPS 궤적 커버리지 기반**, 서버가 재검증 (클라이언트 판정 불신)
- 쿠폰 사용 처리는 QR/매장앱 대신 **매장 PIN 4자리** — 서버 트랜잭션으로 되돌릴 수 없게

## 1. 아키텍처 현황

```
[두루누비 API] ──┐
[관광공사 TourAPI] ─┼─▶ 배치(Fetcher, 이 레포 구현됨) ─▶ raw_durunubi / raw_tour (jsonb 원본 적재)
[기상청/에어코리아] ┘                                          │
                                                                │ (미착수) 변환 배치
                                                                ▼
                                                  regions / courses / pois / merchants
                                                                │
                                                        (미착수) 서비스 API
                                                                ▼
                                                    Android 앱 / 웹 대시보드 (별도 레포)
```

- Supabase (Postgres) + Spring Boot API. RLS는 전 테이블 활성화, anon/authenticated 기본 차단 — 앱 서버는 service_role (DB 슈퍼유저)로 직접
  연결해서 RLS 영향 안 받음.
- 마이그레이션은 Supabase CLI만 사용 (Flyway 없음), JPA `ddl-auto: validate` — 스키마는 SQL 마이그레이션이 소유하고 엔티티는 그걸 검증만 함.

## 2. 원본 데이터 적재 (raw_* 레이어) — **구현 완료**

| 항목                                     | 상태              | 근거                                                                   |
|------------------------------------------|-------------------|------------------------------------------------------------------------|
| `raw_durunubi` (두루누비 courseList)     | ✅ 구현+실행 검증 | 실제 API로 144건 적재 확인                                             |
| `raw_tour` (관광공사 locationBasedList2) | ✅ 구현+실행 검증 | 실제 API로 49건 적재 확인, `endpoint`/`params` 컬럼으로 호출 이력 추적 |

공통 설계 (두 파이프라인이 그대로 공유):

- **Fetcher 인터페이스로 Mock/Real 분리** — 단, `raw_tour`는 실 데이터만 적재하면 되는 파이프라인 이라 Mock은 의도적으로 스킵 (`RealTourContentFetcher`만 존재)
- **delete-all-then-insert** — 매 실행마다 전체 삭제 후 재삽입. API 실패/빈 응답이면 삭제 자체를 안 함 (`@Transactional` + 빈 리스트 가드 이중 방어)
- **item 배열/단일객체 방어 파싱** (`normalizeToNodeList`, `ingest.utils`에 공통 유틸로 추출)
- **`LoggingRestClientCustomizer`** — Boot 자동설정 `RestClient.Builder`에 로깅 인터셉터만 얹는 방식 (직접 `RestClient.builder()`로 새로 만들면
  `spring.http.clients.*` 타임아웃 설정이 무시된다는 걸 실제로 겪고 확정한 패턴). `serviceKey` 등 민감 파라미터는 로그/저장 데이터에서 마스킹/제외 (`@JsonIgnore`)
- 두루누비/TourAPI 모두 `data.api.service-key`(공공데이터포털 공용 키)를 공유

프로파일: `batch-durunubi`(배치 진입점) + `durunubi-real`(Real Fetcher 활성화, 기본은 Mock). TourAPI Fetcher/Runner도 현재 같은 프로파일을 재사용
중 — 프로파일명이 "두루누비 전용"처럼 읽혀서 나중에 세 번째 외부 API가 붙으면 헷갈릴 수 있다는 점은 알려진 개선 후보 (코드리뷰에 기록됨).

## 3. 도메인 변환 레이어 (raw → 서비스 테이블) — **설계 중 / 대부분 미착수**

| 테이블               | 상태                                                        |
|----------------------|-------------------------------------------------------------|
| `regions`            | 🟡 스키마 확정 + 데모용 3건 실데이터 적재됨(서울/일산/거제) |
| `courses`            | ⬜ 미착수 (0건)                                             |
| `pois` / `merchants` | ⬜ 미착수                                                   |

### 3.1 `regions` — 시군구 단위 지역 마스터

처음엔 "raw_durunubi에서 파생"으로 접근했다가, 설계 검토 중 **정적 참조 데이터**로 방향을 바꿨음 — `stamps`/`coupons`/`merchants`/
`region_weather_current`/`running_index` 5개 테이블이 전부 `region_id`를 참조하는데, 이게 raw_durunubi와 1:1이면 "같은 지역인데 코스마다 스탬프/쿠폰이
갈라지는" 문제가 생기기 때문 (자세한 근거는 이 세션 논의 기록 참고, 요약하면 지역은 여러 코스를 묶는 상위 집계 단위여야 스탬프 투어 게임화가 성립함).

현재 스키마: `id, name, sigun, center_lat, center_lng`

- `sigun`: `raw_durunubi.raw_payload->>'sigun'` 원문과 1:1 매칭되는 키 (예: `"경남 거제시"`) — 나중에 `courses` 변환 배치가 이 값으로 조인
- `name`: 표시용 상위 지역명 (예: "서울") — 같은 `name` 아래 `sigun`이 여러 행으로 늘어날 수 있는 구조 (예: 서울에 구가 여러 개 생기면 `name='서울'` 행이 여러 개)
- 원래 있던 `sido`/`sigungu` 분리 컬럼과 `unique(sido, sigungu)` 제약은 이 과정에서 제거됨 — 현재 `regions`에는 **유니크 제약이 없는 상태** (재적재 시
  delete-all-then-insert 패턴을 쓰는 게 안전한 이유)
- `center_lat/lng` 소스: raw_durunubi의 `gpxpath`(GPX 파일)를 실제로 다운로드해서 좌표를 뽑아내는 방법을 조사/검증까지 했음 (`note/gpx-tech.md`) — 다만 공모전
  데모 범위가 서울/일산/거제 3개로 좁혀지면서, 지금 적재된 3건은 GPX 계산이 아니라 잘 알려진 지역이라 대략적인 실측 좌표를 바로 채워 넣은 것. GPX 기반 자동 계산 방식은 지역이 더 늘어날 때 재사용
  가능한 옵션으로 남아있음.
- 적재 방식: 현재 `ai/regions_seed.sql`(plain SQL, Supabase 마이그레이션 아님)을 로컬 DB에 수동 적용한 상태 — **원격/정식 마이그레이션 반영 여부는 아직 결정 안 됨**

### 3.2 `courses` — raw_durunubi → courses 변환 (미착수)

`courses.region_id`가 `regions`를 FK로 요구하므로 `regions` 데이터가 먼저 있어야 시작 가능 (현재 데모 3개 지역은 준비됨). 아직 실제 변환 배치 코드는 없음 — 다음 착수 후보.

### 3.3 `pois` / `merchants` — raw_tour → 변환 (미착수)

기획서 방향: TourAPI `locationBasedList`(음식점 contentTypeId=39, 쇼핑 38)로 코스 종점 반경 매장을 자동 시딩해서 "제휴 매장 (예시)" 라벨로 노출 (실제 제휴는 안 맺고,
실데이터 기반으로 화면만 진짜처럼 보이게). `raw_tour` 원본 적재까지는 됐고, `pois`/`merchants`로의 변환 로직은 미착수.

## 4. 공통 인프라 (API 계층) — **구현 완료**

| 컴포넌트                 | 역할                                                                                                                                                          |
|--------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `CommonResponse<T>`      | 성공 응답 표준 래퍼(`data`, `message`). 실패는 기존 `ErrorResponse` 재사용(에러 전용 `CommonResponse.error()`는 의도적으로 안 만듦 — 불필요한 null 필드 방지) |
| `GlobalExceptionHandler` | `@RestControllerAdvice`. `BusinessException`/`MethodArgumentNotValidException`/미처리 `Exception` 각각 핸들링, `ErrorCode`에서 HTTP 상태코드 결정             |
| `ErrorCode`              | 현재 공통 에러 2종(`INVALID_INPUT`, `INTERNAL_ERROR`)만 정의, 인증 관련 코드는 TODO로 비워둠                                                                  |
| `SwaggerConfig`          | OpenAPI 문서 생성 + Bearer(JWT) `SecurityScheme` 전역 등록. **주의**: 이건 문서 메타데이터일 뿐, 실제 JWT 검증 로직은 없음(아래 5번)                          |
| `SecurityConfig`         | `anyRequest().authenticated()`가 기본 — `/actuator/**`, `/swagger-ui/**`, `/v3/api-docs/**`, `/test/**`만 예외 허용                                           |

`/swagger-ui/index.html`에서 API 문서 확인 가능. `TestController`(`/test`, `/test/login`)는 Swagger 문서화 동작을 검증하기 위한 스캐폴딩 컨트롤러 —
실제 기능 컨트롤러 아님.

## 5. 인증/인가 — **미착수** (기획: 카카오 로그인 → 서버 JWT)

- `build.gradle.kts`에 `jjwt-api`/`jjwt-impl`/`jjwt-jackson` 의존성은 추가돼 있지만, **토큰 발급/검증 로직은 아직 없음**
- `TestController.login()`은 인증 없이 호출 가능한 더미 엔드포인트 — 아이디/비밀번호를 받아 고정 문자열 (`"토큰adsfasfqewr"`)을 반환할 뿐, 실제 로그인이 아님.
  Swagger에서
  `@SecurityRequirements`(빈 값)로 전역 인증 요구사항을 이 엔드포인트만 예외 처리해두는 패턴을 미리 검증해본 것
- `users` 테이블 (카카오ID 기반)은 마이그레이션에 이미 존재, 실제 가입/로그인 플로우 미구현
- 카카오 로그인 SDK 연동은 Android 앱 쪽 작업 — 이 백엔드는 카카오 토큰을 받아 검증하고 자체 JWT를 발급하는 엔드포인트를 준비해야 함 (미착수)

## 6. 코스 완주 인증 — **이 레포 범위 밖 다수, 스키마만 존재**

기획 확정 사항 (요약, 상세는 `기능명세참고.md` B장 참고):

- Android가 `FusedLocationProviderClient` + Foreground Service로 궤적 수집, 노이즈 필터링 (accuracy>25m 폐기, 순간속도>8m/s 폐기, 이동거리<3m
  무시) 후 서버로 업로드
- 완주 판정: 코스 GPX 포인트의 85% 이상이 사용자 궤적 30m 이내 대응점 + 진행방향 일치 + 평균 페이스 3~12분/km — **서버가 재계산해서 최종 판정** (클라이언트가 보낸 "완주함"을 그대로 안
  믿음)
- 부정 방지: Mock location 차단, Activity Recognition API (차량 이동 비율 체크)는 앱 책임, 서버 재검증이 마지막 방어선

이 백엔드가 준비해야 할 것 (미착수):

- 궤적 업로드 API, 완주 판정 재계산 로직
- `run_sessions`/`run_tracks` 테이블은 마이그레이션에 이미 존재 (스키마만) — 서비스 로직/API 없음

---

## 7. 스탬프/쿠폰 — **미착수, 스키마만 존재**

- 스탬프: 완주 인증 성공 시 해당 코스의 `region_id`에 스탬프 적립 (`stamps` 테이블, `unique(user_id, region_id)`)
- 쿠폰: 스탬프 조건 충족 시 발급 (유니크 코드+유효기간) → 매장 PIN 4자리 입력으로 사용 처리 (서버 트랜잭션, `used` 상태로 불가역 전환) → 정산 연동은 로드맵 서술만, 구현 범위 아님
- `stamps`/`coupons`/`merchants` 테이블은 마이그레이션에 이미 존재, 서비스 로직 전부 미착수

---

## 8. 날씨/러닝지수 — **미착수, 스키마만 존재**

- 기획: 기상청+에어코리아 데이터를 크론으로 시군구 단위 하루 3~4회 수집 → `region_weather_current`
  캐싱 (region당 최신 1행)
- 러닝지수 = 체감온도+강수확률+풍속+PM10/PM2.5 가중합 (0~100점) → `running_index`에 이력 저장, 캐치프레이즈 ("오늘 서울 65점 vs 강릉 92점")의 근거 데이터
- Fetcher/배치/계산 로직 전부 미착수 — `raw_durunubi`/`raw_tour`와 같은 배치 패턴 (Mock/Real Fetcher, `LoggingRestClientCustomizer` 재사용)
  그대로 적용 가능할 것으로 예상
