# 티켓 리뷰

## 목적

지금까지 작업한 변경사항이 `current-ticket.md`에 정의된 완료 조건을 충족하는지 검토하고, 결과를 `ai/code-review/`에 기록한다.

**코드는 직접 수정하지 않는다 — 리뷰만 작성한다.** (Edit 도구 권한 자체가 없음)
이 프로젝트는 학습 목적이 있어서, 발견한 이슈를 고치는 건 항상 작업자 본인 몫이다. 자세한 원칙은 `CLAUDE.md` 참고.

## 1단계: 컨텍스트 파악

1. `current-ticket.md`를 읽고 지금 진행 중인 티켓의 작업 내용과 완료 조건을 파악한다.
2. `CLAUDE.md`가 있으면 함께 읽어 프로젝트 컨벤션을 파악한다 (예: JPA 엔티티는 data class 금지, raw 테이블 delSert 정책, Fetcher 인터페이스로 Mock/Real 분리하는
   패턴 등 — 실제 내용은 파일 기준).
3. `develop-ticket.md`를 참고해 이 티켓이 전체 진행 상황에서 어디쯤인지 확인한다 (선택).

## 2단계: 변경사항 확인

- 인자 ($ARGUMENTS)가 주어졌으면 그 기준 (브랜치/커밋)과 비교해서 diff를 확인한다 (예: `git diff $ARGUMENTS`).
- 인자가 없으면 커밋되지 않은 워킹트리 변경사항을 기준으로 한다 (`git status --short`, `git diff HEAD`).
- 변경된 파일 목록과 각 파일의 실제 diff 내용을 모두 확인한다. diff만으로 문맥 파악이 안 되면 변경된 파일 전체를 Read로 열어본다.

## 3단계: 리뷰 기준

아래 관점으로 변경사항을 검토한다:

1. **완료 조건 충족 여부** — `current-ticket.md`의 완료 조건 항목을 하나씩 대조해서 충족 / 미충족 / 일부충족으로 표시한다.
2. **정확성·버그** — 로직 오류, 예외 처리 누락, null/빈 값·경계값 처리 누락 등.
3. **프로젝트 컨벤션 준수** — `CLAUDE.md`에 명시된 규칙, 기존 코드의 패턴과의 일관성.
4. **코틀린다움 (idiomatic)** — 학습 목적이 있으므로, Java 스타일을 코틀린답게 바꿀 수 있는 부분이 있으면 "왜 그게 더 나은지"까지 설명하며 짚는다 (예: 널 아님 단언 연산자 대신 안전 호출
   (`?.`)/엘비스 연산자, 불필요한 `var` 대신 `val`, 반복문 대신 컬렉션 함수 등).
5. **테스트** — 테스트가 함께 작성됐는지, 없다면 어떤 케이스가 필요한지 제안한다.

## 4단계: 리뷰 결과 기록

- `ai/code-review/` 디렉토리가 없으면 만든다.
- 파일명 규칙: `ai/code-review/{current-ticket.md 제목을 슬러그화}_{YYYY-MM-DD}.md`
  (예: `ai/code-review/durunubi-courselist-batch_2026-08-12.md`)
- 같은 날 같은 티켓으로 두 번째 리뷰를 실행하면 파일명 끝에 `_v2`처럼 버전을 붙여 이전 리뷰를 덮어쓰지 않는다.
- 아래 템플릿으로 작성한다:

```markdown
# 코드 리뷰: {티켓 제목}

- 리뷰 일시: {날짜}
- 대상 변경: {커밋/브랜치 범위 또는 "워킹트리 변경사항"}
- 변경 파일: {목록}

## 완료 조건 대조

- [ ]/[x] {완료조건 1} — {충족 여부와 근거} - [ ]/[x] {완료조건 2} — {충족 여부와 근거}

## 발견한 이슈

### 🔴 반드시 확인 (버그·로직 오류)

- {구체적 파일:라인, 문제, 왜 문제인지}

### 🟡 개선 제안 (컨벤션·가독성·코틀린다움)

- {구체적 제안과 이유}

### 🟢 잘한 점

- {있다면 짧게}

## 다음 액션

- {수정이 필요하면 무엇을 어떻게}
- 완료 조건을 모두 충족했다면: develop-ticket.md 상태 갱신 및 다음 티켓 준비를 제안
```

## 5단계: 요약 출력

파일 저장 후, 채팅에는 저장 경로 + "반드시 확인" 항목 개수 + 핵심 이슈 1~2줄만 요약해서 보여준다. 리뷰 본문 전체를 채팅에 다시 출력하지 않는다 — 파일이 원본이다.
