# start-ticket

목적: `develop-ticket.md`에 있는 티켓 목록 중 **가장 위에 있는(첫 번째) 미완료 티켓**을 골라,
실제 개발에 바로 착수할 수 있는 수준의 상세 구현 계획으로 전개해서
`ai/current-ticket.md`에 작성한다.

이 커맨드는 코드를 작성하지 않는다. **구현 계획만** 세운다. 실제 구현은 개발자가 직접 한다.

---

## 절차

### 1. 대상 티켓 선정
- `develop-ticket.md`를 읽는다.
- 목록 순서상 **첫 번째로 등장하는, 상태가 "시작전" 또는 미완료 표시인 티켓**을 대상으로 삼는다.
    - 이미 "진행중"/"완료"로 표시된 티켓이 맨 위에 있어도 건너뛰고 그 다음 미완료 티켓을 찾는다.
- 선행 티켓(의존성)이 명시되어 있는데 그게 아직 미완료 상태면, 이 사실을 사용자에게 먼저 알리고 계속 진행할지 확인받는다.
- 대상 티켓을 찾지 못하면(전부 완료 상태) "진행할 미완료 티켓이 없습니다"라고 보고하고 종료한다.

### 2. 컨텍스트 수집 (작성 전 필수)
계획을 만들기 전에 아래를 실제로 확인한다. 추측해서 쓰지 않는다.

- 티켓 본문에 명시된 완료 조건, 작업 내용, 관련 API/모듈을 정리한다.
- `CLAUDE.md`를 읽어 이 프로젝트의 아키텍처 규칙(MVVM/Compose/코루틴 컨벤션 등)을 확인한다.
- `기능명세.md`가 있으면 관련 화면/기능 설명을 참고한다.
- 티켓이 다루는 영역의 **기존 코드**를 실제로 찾아 읽는다.
    - 예: "코스 목록 화면" 티켓이면 이미 존재하는 `CourseListScreen`, `CourseViewModel` 등 관련 파일을 탐색
    - 완전 신규 기능이면 인접한 기존 패턴(다른 화면의 ViewModel/Repository 구조)을 참고 대상으로 삼는다.
- 백엔드 API를 호출하는 티켓이면, 관련 API 스펙(문서 또는 백엔드 코드)을 찾아 실제 요청/응답 형태를 확인한다. 못 찾으면 "API 스펙 미확인"으로 명시하고 넘어간다.
- 이 티켓이 선행 티켓으로 걸려있는 다른 티켓이 있는지 `develop-ticket.md`에서 확인해, 이번 구현이 어디까지 책임져야 하는지 범위를 명확히 한다.

### 3. `ai/current-ticket.md` 작성
`ai/` 디렉토리가 없으면 생성한다. 기존에 `current-ticket.md`가 있으면 **덮어쓰기 전에 사용자에게 확인**한다 (이전 티켓 작업이 아직 안 끝났을 수 있음).

아래 형식으로 작성한다.

```markdown
# 현재 작업 티켓: {티켓명}

- 노션 링크: {있으면}
- 소속 마일스톤: {있으면}
- 담당 영역: {프론트엔드/백엔드/인프라}
- 선행 티켓: {있으면, 완료 여부 표시}

## 목표
이 티켓이 끝났을 때 되어 있어야 하는 상태를 한두 문장으로.
(검증 가능한 문장으로 — "구현함"이 아니라 "~하면 ~가 동작함")

## 완료 조건 (Definition of Done)
- [ ] (티켓 원문 기준, 없으면 이번에 구체화해서 작성)
- [ ] ...

## 구현 순서
번호를 매겨 실행 순서대로. 각 단계는 "무엇을, 어느 파일/모듈에" 수준까지 구체적으로.
1. ...
2. ...
3. ...

각 단계가 서로 의존관계가 있으면 명시 (예: 2번은 1번의 Repository 인터페이스가 있어야 함)

## 파일별 작업 내역
관련될 것으로 예상되는 파일들을 나열하고 각각 무엇을 할지 설명.

| 파일 경로 | 작업 내용 | 신규/수정 |
|---|---|---|
| ... | ... | ... |

## 참고할 기존 코드
이번 구현과 패턴이 비슷한 기존 파일이 있으면 경로와 참고 포인트를 명시.
(없으면 "참고할 기존 패턴 없음 — 신규 구조" 라고 명시)

## API 연동 (해당되는 경우)
- 엔드포인트, 요청/응답 형태
- 스펙 미확인 상태면 그 사실과 확인 방법(누구에게 물어봐야 하는지)을 명시

## 주의사항 / 흔히 하는 실수
CLAUDE.md의 개발 규칙 중 이 티켓에서 특히 걸리기 쉬운 지점을 골라서 적는다.
(예: 위치 권한 미허용 상태 크래시, 코루틴 스코프, 화면 회전 시 상태 유지 등 — 티켓 성격에 맞게)

## 테스트/검증 방법
구현 후 무엇을 어떻게 확인하면 되는지. 실기기 테스트가 필요한 티켓이면 그 사실을 명시.

## 미확정 사항
계획 세우다가 판단이 안 서는 부분이 있으면 여기 나열하고, 본문 맨 끝에서 사용자에게 질문으로 다시 제시.
```

### 4. `develop-ticket.md` 상태 갱신
대상 티켓의 상태를 "시작전" → "진행중"으로 변경한다. (다른 내용은 건드리지 않음)

### 5. 최종 보고
- 어떤 티켓을 선정했는지와 선정 이유(순서상 첫 미완료 티켓)
- `ai/current-ticket.md` 작성 완료 알림
- 조사 중 확인이 안 된 사항(API 스펙 미확인, 참고할 기존 코드 없음 등)이 있으면 목록으로 정리해서 질문

---

## 금지사항
- 이 커맨드에서 실제 코드를 작성하거나 파일을 구현하지 않는다 (계획만 작성).
- `develop-ticket.md`의 다른 티켓 항목이나 이미 완료된 티켓의 내용을 수정하지 않는다.
- 완료 조건이나 구현 순서를 근거 없이 지어내지 않는다 — 티켓 본문/CLAUDE.md/기존 코드에서 실제로 확인한 내용 기반으로만 작성하고, 불확실하면 "미확정 사항"으로 분리한다.
